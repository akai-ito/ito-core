# Golden transcripts

One transcript per scenario: everything that crosses the API, step by step, as JSON Lines. The
server's integration tests replay them through the real API with a scripted engine, and apps feed
the events to their own state to check what they show. They are generated by
[../tools/scenarios.ts](../tools/scenarios.ts) and checked in CI by
[../tools/check.ts](../tools/check.ts); don't edit them by hand.

## Lines

The first line is a header:

```json
{"transcript":"07-stop","start":"2026-10-12T08:41:00.000Z","scenario":7,"title":"Stop","summary":"…","guarantees":["G3","G7","G9"],"app":{"cursor":"e_0006_13823"}}
```

`start` anchors the steps in time: each step's `at` counts milliseconds from it. `guarantees` names
the [guarantees](../guarantees.md) the scenario shows. `app` is where the app starts: the last event
it applied (`cursor`) and, where it matters, the oldest message it has cached (`oldest_cached`).

Then come `given` lines, the events already in the server's log when the scenario starts, followed
by the steps. Each step has `at`, in milliseconds from the start, and exactly one of:

| Field | A step where… |
| --- | --- |
| `app` | the app sends a request: `method`, `path`, and `headers` and `body` where they matter. An upload names its bytes instead: `body_file`, a file in [files](files), or `body_size`, that many bytes |
| `server` | the app receives the response to its last request: `status`, and `headers` and `body` where they matter; `"lost": true` means it never reached the app |
| `event` | the app receives an event from `GET /v0/events` |
| `world` | something happens outside the API |
| `push` | the server sends a notification to a registered device: `device`, `level`, and the `notification` as the device shows it once decrypted (see [the push schema](../push.schema.json)) |
| `socket` | a frame on a call's stream: `from` (`app` or `server`) and one of `frame`, a text frame as in [the stream schema](../stream.schema.json); `audio`, the app's microphone audio as a file in [files](files) (16 kHz 16-bit PCM); `audio_ms`, how much of Ari's voice arrived; or `closed`, the server closing the socket with that code and `reason` |

Events keep the server's own time in their `at` field, so an event replayed after a disconnect
shows when it really happened. Requests other than the first connection leave out the
`Authorization` header; every one of them carries it, except `POST /v0/pair`, which needs none. A
request that shows its own `Authorization` header uses the token it names.

## World markers

| Marker | What happens |
| --- | --- |
| `offline`, `online` | the network drops and returns; the stream breaks and requests fail |
| `app_closed`, `app_opened` | the app leaves the screen and comes back; its stream closes meanwhile. `from: notification` means a tap on a notification opened it |
| `app_scrolled_up` | you scroll back while a reply streams; nothing changes on the wire |
| `network_stall` | the network holds events back and releases them together at `until` |
| `server_restarted` | the server restarts and keeps its data |
| `server_restored` | the server restarts from a backup whose log ends at the event `to` |
| `engine_compacting` | the agent's engine compacts its context and can't take new input until `until` |
| `engine_stalls` | the agent's engine stops responding |
| `notifications_allowed` | you allow notifications when the app offers them |
| `notification_answered` | you answer an ask from its notification, without opening the app |
| `pairing_code_shown` | `ito pair` shows a QR code holding the address and this `code` |
| `voice_loading`, `voice_ready`, `voice_failed` | the server's voice starts loading, becomes ready, or fails; `reason` says why it isn't ready |
| `you_say` | what the server's recogniser will hear in your next audio on the call's stream: the turn's `text`, and the live captions on the way in `heard` |
| `voiceprint_learnt` | the server has learnt your voice from your calls |
| `memory_holds` | memory already holds these `pages` |
| `capability_on` | a capability is set up with these `values` and switched on |
| `web_has` | the web serves the picture at `url` |
| `agent_calls` | the agent calls one of Ito's tools: `tool` and `input`, and what it `returns` where it matters |
| `you_approve` | you approve the `code` a capability's connection showed, at the provider; the server picks up the token at its next poll, within 5 seconds |
| `ari_keeps_up` | what Ari will answer when the server asks it, aside, to keep a thing up with your ticks and choices: its `changes`, `summary` and `note` |
| `topic_decided` | what the quick model will answer when the server asks it, after the turn, whether the subject changed: the new topic's `label` |

## Ids

Ids are deterministic so that tests can compare transcripts exactly. They are still opaque: the
`e_0007_48213` shape is only how this generator writes them, and a client must never parse one. A
server may compare transcripts with its ids renamed, as long as it never reuses one.
